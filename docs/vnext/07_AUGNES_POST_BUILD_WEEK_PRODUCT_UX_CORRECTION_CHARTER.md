## Why the correction program existed

The Build Week implementation proved an operational continuity Core and a
reference operator interface. Product drift occurred when engine structure,
protocol sequence, and evaluation surfaces became default user information
architecture. Users had to interpret internal taxonomy before their own intent,
current meaningful work, result, uncertainty, and next decision.

C0–C9 correct that projection while preserving Core meaning, current data,
lineage, authority, recovery, and working behavior until each replacement is
proven. The program is a temporary migration and closeout mechanism, not the
permanent product doctrine.

## C9 scope boundary

C9 may be proposed only as separately authorized, proof-backed replacement and
compatibility work. It must not be inferred from the word “cleanup,” from old
names, from missing navigation, from static import reachability, or from the
existence of historical/research residue.

Every proposed C9 disposition must name the exact surface or compatibility
family and choose one outcome:

- retain as active compatibility;
- absorb into the current owner;
- redirect to a proven replacement;
- demote from active product presence;
- remove after all proof passes.

C9 must preserve:

- current user data and project isolation;
- Core/protocol and authority meaning;
- migration, backup, restore, recovery, update, and run reconciliation;
- exact source, decision, Transition, and later-context lineage;
- required package, host, MCP/App, operator, and external-consumer behavior;
- rollback or recovery from a failed replacement.

## Required C9 proof

Before changing a compatibility path, the C9 pull request must provide:

1. **Current owner and behavior** — exact route, component, API, type, schema,
   contract, package, fixture, script, document, or external reference.
2. **Replacement parity** — which current product responsibility absorbs the
   user need and how equivalent authority/data behavior is preserved.
3. **Consumer proof** — static, dynamic, string-addressed, deep-link, package,
   host, MCP/App, fixture, archived evaluation, and known external consumers.
4. **Data proof** — live data population, readers/writers, migrations, export,
   import, backup, restore, rollback, and historical replay.
5. **Authority proof** — no candidate, projection, recommendation, decision, or
   execution result changes semantic or execution authority.
6. **User-path proof** — no added peer destination, default concept, protocol
   burden, false attention, or required Inspector/internal-ID work.
7. **Verification proof** — exact changed paths, focused tests, planner-selected
   Local Canonical verification, and complete owned-process cleanup.
8. **Disposition and rollback** — what is removed, retained, redirected,
   absorbed, or demoted, plus how failure is recovered.

Unknown consumers, data, or authority effects block removal. They are not
evidence that a path is obsolete.

## C9 non-goals

C9 is not authority to:

- redesign Core, schemas, migrations, protocols, or persistence;
- invent a new product topology, route family, research engine, or authority
  layer;
- delete historical or research material merely to reduce repository size;
- turn research output into truth, accepted Perspective, decision, Transition,
  or execution authority;
- remove compatibility without replacement and rollback proof;
- publish evidence, release, merge, or change repository settings without their
  own explicit authorization.

## Closeout and retirement

The C0–C9 program closes only when:

- C9 has received separate explicit authorization;
- each in-scope compatibility family has an approved proof-backed disposition;
- replacement parity, consumers, data, authority, user path, rollback, and exact
  verification are reviewed;
- no unresolved C-stage requirement remains;
- current sequencing in `03` records the completed outcome;
- durable rules needed after C9 have been absorbed into `01`, `02`, `04`,
  `AGENTS.md`, or a bounded active implementation contract.

After closeout, this file should be reduced to a short historical pointer or
moved to history in a separately reviewed documentation change. It must not
remain a competing permanent product authority.
