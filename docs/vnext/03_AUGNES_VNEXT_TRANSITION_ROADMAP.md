# Augnes current implementation and sequence

## Role

This is the sole active owner of completed, current, next, later, and research
sequencing. It does not define product doctrine, Core/protocol semantics,
evaluation criteria, or the detailed C0–C9 proof contract.

Checked-in code and runtime behavior remain the source of truth for what is
implemented. A target named here is not implemented merely because it appears
in the roadmap.

## Phase-state rule

- **Completed** means the implementation or documentation outcome was reviewed
  and merged.
- **Current** means explicitly authorized work is open on its named branch or
  pull request.
- **Next** means a candidate for separate explicit authorization; it is not
  authorized by appearing here.
- **Later** means durable product direction without an approved implementation
  phase.
- **Research** means bounded investigation or capability whose output remains
  non-authoritative.
- **Compatibility/history** means retained behavior or evidence, not current
  product direction.

An issue defines a phase specification. Its linked pull request is the outcome
record. A phase becomes completed only when that pull request merges. This
lifecycle wording remains truthful before and after merge without treating a
Draft PR as completed runtime.

## PC1 phase lifecycle

A potential next phase is one bounded product-continuity implementation slice,
chosen only after explicit review of PC1 runtime evidence. Candidate
responsibilities include timeline-first work detail, bounded relationship
exploration, or a more conversational GuideBrief.

Any such phase must:

- preserve Core/protocol and authority boundaries;
- distinguish current behavior from target direction;

## Compatibility and historical work

Current compatibility paths remain until a separately authorized phase proves
replacement and safe retirement. Historical plans, milestone records,
submission material, fixtures, archived packages, old Workplane/Cockpit names,
legacy MCP tools, and unmerged research branch residue do not become current
authority because they remain reachable or referenced.

Later documentation, code, fixture, script, schema, route, package, or branch
reduction must be split into reviewed proof-backed batches. Unknown external
consumers, data population, dynamic imports, archived evaluation use, and
retention requirements remain unresolved rather than being converted into
deletion claims.
