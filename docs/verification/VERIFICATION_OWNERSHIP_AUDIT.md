## Suspicions resolved or left open

- **Incomplete coverage:** confirmed for this exact harness family. Fixed by
  owner mapping, not removing tests.
- **Native-host mappings shadowed:** confirmed: high-risk matching precedes
  targeted matching, so several native-host source entries cannot select their
  nominal narrow owner. Their registered test-only entry points can. Do not
  reverse precedence globally: adapter, credential, selection and managed-store
  consumers span integration, operability and Browser execution.
- **Research mixed with production:** labels are mixed; responsibilities are
  not interchangeable. Gateway/adapter imports and persisted continuation
  consumers require retention. Standalone live research is already separate.
- **Literal duplication:** standalone strategy-composition wrappers invoke the
  same conformance functions, but are not separately in the default suite.
  `--operator-adapter-only` is disjoint from default Verify lifecycle;
  `--sr3-lifecycle` adds a production chain while the baseline adapter mode owns
  a distinct criterion-isolation branch. No entire equivalent execution was
  found safe to absorb.
- **Browser/golden overlap:** manifest contracts partition 69 project,
  136 operator and 29 continuity detailed fields. Golden has zero detailed
  fields and explicitly forbids those matrices. It remains composition proof.
- **Operability overlap:** the responsibility owner explicitly repeats runtime,
  MCP, isolated resources, zero egress and natural cleanup per independently
  owned child. Those are required preconditions, not duplicate success cases.
- **Framework recursion:** planner/executor/owner-manifest changes still force
  broad verification. This PR deliberately retains that self-change fence.
- **Dependency/build cost:** both installations together measured 7.095s in
  PR #1207 versus 1,784.955s for integration plus operability. Avoiding installs
  would trade provenance for little savings. Build remains unchanged in Full.

## Target model and remaining granularity

Use existing architecture layers: (1) universal exact provenance/admission;
(2) owner-targeted static/correctness plus detailed Browser proof;
(3) high-risk boundary composition; (4) separately authorized runtime/platform
qualification; (5) research/evaluation commands; (6) explicit complete-system
Canonical. Do not add a new parallel runner or infer ownership from names.

The `changed` mode's `full-canonical` label can still select a Browser subset
through the pre-existing Browser map. Explicit `full` always forces every
permanent Browser phase. The examples below show actual phase inventories,
rather than assuming that the plan label always means fourteen phases.

Unit and authority are still coarse aggregates. Extracting a smaller static
Browser-policy phase, defining closed runtime ownership, and separating
report-only research from shared codecs are future candidates. They need their
own registration/consumer/replacement proof. This change does not declare all
unmatched paths intrinsically cross-cutting.

## Conservative verification and risks

This PR changes verification ownership, so its own deciding proof must remain
explicit Full Canonical, with the pre-existing full executor/suite/phase,
dependency, Browser, environment, lifecycle and receipt source unchanged.
Compare those source inventories against the exact audit base before running;
do not accept this modified manifest's narrow self-assessment. Run focused
planner/contract/executor/receipt checks during development, independently
review the final diff for missing consumers, then commit a clean exact head,
run `verify:local:full -- --base <base> --head <head>` once and validate the
receipt. The PR records actual results, exact identity, commands and cleanup.

Remaining risks: future reverse consumers can outgrow this exact mapping;
unit/authority remain coarse; runtime-owner shadowing and unknown research
paths still overselect; platform/browser/environment timing varies. The optional
comparison reuses the unchanged phase executor to expand phase names and is
diagnostic, not independent attestation. No live provider/candidate/research,
hosted CI, release/platform certification, deployment or publication is implied.
